# CLAUDE.md

Context for any AI coding agent working in this repository. Read this before making changes.

## What this is

A small network of Claude Code CLI instances, each running headlessly on its own machine, each with its own voice (Piper TTS) and an animated face (a browser userscript overlay). One machine is the **hub** (currently the agent "Oscar"), any number of others are **nodes** (currently "Nova") connected to the hub over mutual-TLS. The hub takes microphone input, decides which agent should answer, and coordinates a shared "main display" agents can show visual content on.

## Repo map

| File | Role |
|---|---|
| `agent-bridge-server.js` | The hub process. Routing, follow-up chains, the display queue, everything Oscar-specific. Never synced to a node. |
| `node-agent.js` | Runs on every node. Connects to the hub, runs its own Claude Code sessions, speaks locally. |
| `agent-net.js` | The mutual-TLS transport shared by hub and nodes (length-prefixed JSON framing over TLS 1.3). |
| `followup-tag.js` | Shared: the `[FORWARD: Name]` / `[PRESENTATION: url]` / `[SLIDE]` / `[PROVISION: {...}]` / `[IDENTITY: {...}]` marker regexes, and `buildSystemPointer` — the one short paragraph every turn's system prompt carries, pointing the agent at its skills. The marker rules themselves live in `agent-skills/`. |
| `deck-runtime.js` / `.css` | The slide engine for multi-slide presentations, served by every overlay server at `/deck.js` and `/deck.css`. Runs inside the presentation iframe, not in the overlay's privileged context; every presentation page is served with `Content-Security-Policy: sandbox` from a port of its own, so a deck never counts as the machine's own page. Scales a slide down when its content does not fit the screen. |
| `agent-skills/` | Source of the agents' skills: `network`, `presentation`, `inbox`, and the hub-only `new-agent`. Never loaded from here — each agent copies its set into its home at startup. Deliberately not in `.claude/skills`; `agent-skills/README.md` says why. |
| `speech.js` | Speech synthesis and local playback: Piper on Windows and Linux, the phone's own TTS engine on Android (Termux). Playback picks a blocking player per platform, because slide advancing hangs off the player's exit. On a phone that is the main display, audio received from another agent plays through `play-audio`; without it the slide text is spoken in the phone's own voice, and a phone that presents elsewhere sends its slides as text. Language-agnostic — the voice decides. |
| `overlay-server.js` | Local HTTP+WebSocket server each machine runs for its own browser overlay; also serves `faces/*.js` and, from a port of its own, the presentation pages it is showing (`/shown/...`). Answers this machine only. |
| `agent-face-overlay.user.js` | The face: mic input, speech recognition, face rendering, presentation iframe. Served by every overlay server and loaded by its own page at `http://localhost:8787/`, so no extension is needed; still installable as a Tampermonkey userscript, with a guard so the two never both mount. Reports its screen once per connection as a class (phone, tablet or large, plus a size range for the short and long side) -- never exact dimensions, never the orientation. One file for every agent. |
| `faces/*.js` | Per-agent face definitions (SVG + CSS + mouth animation params). Never exposed to an agent's own write access — see the comment in `overlay-server.js`. |
| `net-config.example.json` | Template for a node's config. The hub's own `net-config.json` only needs `role` and `self`; the hub adds `peers` (which machines may connect) and `agents` (who each of them is) itself as agents are enrolled. |
| `make-certs.sh` | Generates a self-signed identity per machine. No shared CA — every side pins the other's exact certificate fingerprint. Still used for the hub's own identity; new nodes generate theirs during enrollment instead. |
| `enrollment.js` | Pairing-code enrollment: code generation, the scrypt+HMAC proof, and both ends of the short-lived enrollment channel. Read its header before touching the proof. |
| `inbox.js` | Files handed to one agent: chunked transfer over the mTLS link, and the one-line "new file arrived" event an agent gets on its next turn. How to handle the inbox is in the `inbox` skill. |
| `files-page.html` | The drop UI at `http://localhost:8787/files`, hub machine only. |
| `enroll.js` / `enroll.bat` | Run on a NEW machine to join the network. Generates that machine's key pair locally — no private key ever travels. |
| `agent-home.js` | Each agent's home, `~/.aliveagents/<name>/`, outside every repository: generates its skills from `agent-skills/` and keeps the two data files those skills read (`agents.md`, `display.md`) current, and creates the agent's `workspace/` (its own files, write access granted) and `memory/` (reserved for later, not used yet). Its header records why no agent may run inside this checkout. |
| `identity.js` | Gives every newly enrolled agent a face colour and a voice nobody else on the network has, assigned against the whole set rather than per name. A colour is data, validated as `#rrggbb`, never code. |
| `agent-registry.js` | The hub's record of every agent's name and responsibility, keyed by machine: written at enrollment, changed only with `/agent` at the hub. A node's own `agentName`/`domain` merely introduce it to a hub that has no record yet. An agent can ask for a change to its own entry (`[IDENTITY: ...]`); the user accepts or declines it with the buttons on the hub's page (`stage-page.html`) or `/agent confirm|reject`. Its header says why. |
| `permissions.js` | What each agent may do, decided per device on that device's own face page (the shield button) and nowhere else, kept in `~/.aliveagents/.permissions/`. The page only sends the switches it wants; the change is worded here, from `CATALOGUE`, and written only after the device's own confirmation dialog showed that text and the user said yes (`device-confirm.js`). `claudePermissionArgs` is the one place the CLI's permission flags are built; `allowedTools`, `chrome`, `mcpConfig` and `permissionMode` in `net-config.json` are only what a device starts with. |
| `device-confirm.js` | The operating system's own confirmation dialog, showing a text this program wrote: Windows Hello through `UserConsentVerifier` (via Windows PowerShell, parented to the foreground window), `termux-fingerprint` on a phone. Used for permission changes, decision cards and `/agent` typed on the hub's page. On Android 10 and later the fingerprint prompt only comes up over the browser once Termux:API may display over other apps -- without that it hangs with no window at all (found on Android 14, 2026-09-15). |
| `updater.js` | Each agent keeps its own program up to date, by itself -- the hub is not involved, so agents running other code are unaffected. At start and daily it asks the public GitHub repository for the newest `release.json`, accepts only a release signed with the release key (`release-key.pub`) and newer than its own, shows a notice on its face page, and installs only after the device's confirmation dialog named the version. Never touches settings, keys, tokens, sessions, `tools/` or `node_modules/`. Start scripts and package lists that already exist on the device are installed by hand (one that is missing cannot be running and is simply written -- the .bat files on a phone, start-node.sh on Windows); a copy with `.git` (the development PC) never updates itself. A copy deployed by hand should get the `release.json` of the version it matches, or the next check offers that release again over newer hand-deployed files. Exit code 75 asks the start script to start the program again. |
| `publish-release.js` | Signs a release on the PC holding the private release key (`~/.aliveagents-release/`, never in the repository): `--init-key` once, then without arguments -- Windows Hello names the version. Committing and pushing stay separate steps. |
| `claude-cli.js` | Starts the Claude Code CLI for one turn with the message on stdin, and holds the 150,000-character limit for a message. |
| `setup-termux.sh` / `start-node.sh` | Preparing and starting a node on an Android phone (Termux) or on Linux. The setup script documents why Claude Code runs there through a hand-written glibc launcher rather than `grun`. |

## Setting up a dev environment

1. Node.js and the Claude Code CLI (`claude setup-token`) installed and on `PATH`.
2. `npm install`.
3. `sh make-certs.sh` for the hub's own identity. Additional nodes no longer need this, nor any manual certificate copying: ask Oscar to set up a new agent (or run `/provision <name>` on the hub console) and run `enroll.bat <hub-ip> <code> <name>` on the new machine.
4. Copy `net-config.example.json` → `net-config.json` per node and fill it in; the hub's own `net-config.json` is much smaller (see table above).
5. Copy `token.local.bat.example` → `token.local.bat` with a real token. Anything matching `*.local.*` is gitignored — never remove that from `.gitignore`, never commit a real one.
6. A Piper voice model per agent in `tools/piper/voices/`.
7. `start.bat` (hub) / `start-node.bat` (node).

## Conventions this project expects

- **English only, everywhere** — code, comments, console output, prompt text. This was a deliberate full-project migration; don't reintroduce another language into new code.
- **Comments explain *why*, not *what*.** This codebase has a lot of comments documenting non-obvious reasoning and hard-won bugs (dates included where relevant) — match that style, don't add comments that just restate the code.
- **No speculative abstraction.** Small, direct functions; duplication between `agent-bridge-server.js` and `node-agent.js` where their logic is genuinely parallel is intentional, not something to force into a shared module.
- **Deterministic triggers over model judgment, when a cheap reliable signal exists** — e.g. name-matching for routing. Model judgment is preferred specifically where no reliable pattern exists (see the extensive comment in `followup-tag.js` about why there's no regex trigger for "should I present something").

## Things that will bite you if you don't know them

- **On Windows, never `spawn('claude', ...)` directly.** `claude` resolves to a `.cmd` shim, and spawning a `.cmd` file forces the whole command line through `cmd.exe`, which re-parses every argument with its own metacharacter rules — a reply containing both a `"` and an `&` will silently corrupt the call. Both `agent-bridge-server.js` and `node-agent.js` define a `CLAUDE_EXE` constant that resolves the bundled `claude.exe` directly; reuse it, don't spawn `'claude'` as a bare string.
- **An update never replaces a start script under a running program, and hashes read CRLF as LF.** cmd.exe (and bash) read a script at the offset where they left off, so a start script changed while it runs executes from the middle of a line; a release that changes one is marked "install by hand". Git may store and serve a text file with other line endings than the checkout that published it (core.autocrlf), so `contentHash` treats CRLF as LF on both sides -- raw-byte hashes would have failed every update. The restart waits 1.5 s even when idle, or the page that pressed Install never gets its answer (found by the live test).
- **A node listens for itself only while its hub is out of reach** (user's wish 2026-09-22: take the phone along, leave the rest at home). The hub stays the one microphone of the network; a node's face page gets a microphone (`micEnabled`) only after the hub has been unreachable for `OFFLINE_AFTER_MS` (10 s -- the link reports every failed retry, so the count starts at the first and is never restarted) and loses it the moment the link is up again. `overlay-server.js` checks `inputEnabled()` on every `user-input`, not only via the button. A direct turn tells the agent it is alone (`runTask` `options.direct`), and going offline empties the roster and marks the main display offline, so the agent neither promises to hand anything on nor sends a presentation to a screen it cannot reach. The same permissions apply.
- **The message goes to Claude on stdin, never on the command line** (`claude-cli.js`). Windows caps a command line at 32,767 characters, and spawn throws `ENAMETOOLONG` synchronously -- a long pasted text ended Nova's whole process on 2026-09-22. `startClaude` pipes the prompt, turns a spawn that throws into an `'error'` event, and ignores the stdin error of a CLI that exits early. Line breaks in a message now survive (on the command line one once cut a message short). A message above `MESSAGE_MAX_CHARS` (150,000) is turned away in `askAgent` with a sentence in the chat it came from.
- **A node's identity (certs, `self`/`hubName` in `net-config.json`) is separate from its spoken agent name.** Renaming an agent (e.g. Oscar/Nova) never requires new certificates — those are lowercase, machine-level identifiers (`thorsten`, `node2`) kept deliberately independent of the capitalized display name. Name and responsibility belong to the hub, not the node (`agents` in the hub's `net-config.json`, see `agent-registry.js`): the hub attributes every message by the certificate it arrived with and ignores the name written inside it, so no machine can speak, present or finish work in another agent's name.
- **Web addresses never reach the voice.** The web search tool tells the model to end with a "Sources:" list of links, and the voice read them out character by character (2026-09-15). The `sources` skill and one clause in `buildSystemPointer` ask for sources named in the sentence instead; `speakableText` in `speech.js` catches what slips through, inside `synthesizeSpeech` -- the one place every spoken text passes -- so the chat and the bubble still show the reply as written.
- **`PRESENTATION_TAG_RE` is intentionally not end-anchored.** Models occasionally add a trailing remark after the marker; the regex tolerates text on both sides and stitches it back into the spoken reply.
- **Marker regexes tolerate the markdown a model wraps around them.** `SLIDE_TAG_RE` eats optional backticks/asterisks/underscores on both sides — found live on the first real test, where the model copied the code-formatted `` `[SLIDE]` `` from the skill's own example and left stray backticks in the text handed to Piper. Anything leftover next to a marker gets spoken out loud, so match what models actually emit, not just the documented ideal.
- **A multi-slide presentation is one WAV per slide, not one per reply.** `splitSlideSegments` cuts the spoken text on `[SLIDE]`, `speaker.synthesizeAll` renders each segment separately, and `speaker.playSequence` advances the deck in the pause between them. The single-slide case is simply the one-element array — there is deliberately no separate code path for it, in either `agent-bridge-server.js` or `node-agent.js`.
- **`speaker.stopSpeaking()` bumps a generation counter, not just a kill.** Killing the player fires the same `close` event as a segment ending normally, so without that counter an interrupted presentation would carry on to the next slide. Anything added to `playSequence` has to keep respecting it.
- **`present`/`present-request` messages carry `segments[]`, with `audioBase64` kept only for the single-slide case.** That is on purpose: it costs nothing there and lets a machine running an older copy of the project still show a working single-slide presentation. Both sides normalize via their own copy of `normalizePresentSegments`.
- **Where an agent's Claude session runs decides what it loads** (measured 2026-09-14). Claude Code reads `CLAUDE.md` from the working directory *and every parent*, scopes memory and saved sessions per directory, and confines file access to that directory plus `--add-dir` roots — an absolute path in `--allowedTools` grants nothing on its own. On Linux and Android an absolute path inside a permission rule also needs a doubled leading slash, `Edit(//data/...)`: a single slash is read as relative to the project and silently grants nothing (measured on the phone, 2026-09-14). `agentHome.permissionPath` does this; Windows paths are unaffected. An `--add-dir` makes that directory's skills available but does not load its `CLAUDE.md`. So no agent runs inside this checkout any more (it cost about 4,500 tokens per turn, for this very file): each works in its home from `agent-home.js`, or in its `workDir`, and the checkout is always passed as `--add-dir`. That last point is also why agent skills must never sit in this checkout's `.claude/skills` — they would load twice. A saved session records the directory it belongs to and is dropped when that changes, because resuming from a different directory fails.
- **`inbox/` is deliberately NOT under `presented_content/`.** Pages written there travel to whichever screen shows them, which is right for a slide deck and wrong for a photo handed to one agent. `inbox/` is never served; with "Receive files" on, the agent gets `Edit(inbox/**)` so it can still move or tidy what it was given. With it off, the hub refuses uploads to Oscar and a node turns deliveries away with `file-refused`.
- **A connection from 127.0.0.1 is not the user.** `isLocalRequest` keeps the WiFi out of the face server entirely -- but every page the local browser shows connects from 127.0.0.1 too: an agent's presentation, a website an agent put on screen, any other tab. A WebSocket has no same-origin rule. So typing to agents, the chat stream, uploads, `/agents` and the Accept/Decline decisions all require `isOwnPage` in `overlay-server.js`: this machine's address *and* either no `Origin` (a local program) or this server's own `http://localhost:<port>` origin. Found 2026-09-15 by getting `/network` answered for `Origin: https://evil.example`. The stage page refuses to be framed (so its buttons cannot be clickjacked), `/content/` is served sandboxed, and `/agent` commands are refused when they came from the microphone -- and typed on the page, `/agent` and Accept/Decline only take effect once this device's own confirmation dialog has named them (`device-confirm.js`). Nothing on the face server answers the WiFi any more, and the face-state WebSocket refuses every handshake but the own page's -- that stream is a live transcript of what the agent says, and until 2026-09-15 anyone could watch it. Presentations used to be the reason the server answered the WiFi at all: a display fetched the deck over plain http from the machine that wrote it, key in the URL. Now the presenter sends the page itself (`page: { name, html }`, see `readOwnContent`) over mTLS, and the display serves it to its own browser under `http://127.0.0.1:<face port + 100>/shown/<random>/<name>` (`showPage`) -- a port of its own, bound to loopback, so the page is a different site than the face page even if its sandbox header were ever lost. A link to an agent's page that arrives without its page is handed back, never fetched. Real websites are still shown by URL. A sandboxed page has no origin of its own, and Chromium does not let it load anything from this machine -- not even `/deck.js` -- so `inlineDeckAssets` writes the deck engine into the page as it is served; the server tests could not see this, only a real browser did (frame stayed black). Consequence: the face installed as a Tampermonkey userscript on another site no longer works at all; open it at `http://localhost:8787/`.
- **The inbox line is rebuilt from the folder on every turn, not tracked as a pending list.** If the agent moved or deleted a file last turn, a stale list would have it reasoning about something that is no longer there.
- **Provisioning deliberately gives Oscar no new permissions.** Oscar names an intent via `[PROVISION: {...}]`; the hub performs it. Do not "simplify" this by turning on Oscar's command line in code -- that switch is the user's call on his face page, and it would reopen the gap closed on 2026-08-17, on the one agent that listens to the microphone.
- **The enrollment channel is intentionally unauthenticated at the TLS layer** (`rejectUnauthorized: false`, `requestCert: false`). That is not an oversight: neither side has anything to validate against yet. Authentication comes entirely from the code-derived proof, which covers BOTH certificate fingerprints -- remove either fingerprint from the proof and a man in the middle can simply relay it.
- **The pairing code is bound to one name** (`expectedName`). Without that, a valid code could enroll any name, including one that overwrites an existing peer's certificate.
- **`hub.addPeer()` updates two things that must stay in step**: the TLS secure context's `ca` list and the fingerprint `expected` map. Updating only one silently rejects the new node at the other layer.
- **`Skill` is always in `--allowedTools`, whatever the switches say** (`claudePermissionArgs`). Skills are discovered fine in headless `-p` mode (verified live), but once `--allowedTools` narrows the set, an undeclared `Skill` tool means the agent can see the skill and not invoke it.
- **A switched-off tool is forbidden, not just left out.** Claude Code also reads the working directory's `.claude/settings.json`: its allow entries count in a trusted folder, and its `defaultMode` counted even in an untrusted one, so `bypassPermissions` there silently lifted every check (measured 2026-09-15). `claudePermissionArgs` therefore always passes `--permission-mode`, names every switched-off tool in `--disallowedTools` (a forbidden tool is not even offered), and keeps an agent with `projectEdit` out of its project's `.claude/` and `.mcp.json`.
- **Nothing on the face page is trusted with what a change means.** An agent allowed to control the browser can run script on that page and reword it -- swap two labels, and the user grants the command line while ticking "Search the web" (user's requirement 2026-09-15: agents may change nothing on the interface but their own face). So the page only sends the switches, or a card id and yes/no; the agent's own process words the change from its own `CATALOGUE` or the hub's own record, and `device-confirm.js` has the operating system show exactly that text. Passkeys were built first and dropped the same day for this reason: their dialog shows no text. This covers permission changes, Accept/Decline and `/agent` typed on the page; typed into the console window, `/agent` applies directly. Text an agent wrote (a responsibility) goes into a dialog only quoted, shortened and stripped of invisible and bidirectional characters. Settings are read from disk on every turn; a file that cannot be read gives `MINIMAL`, never the seed. `ALIVEAGENTS_CONFIRM_COMMAND` swaps the dialog for a script -- only the sandbox tests set it, and the console says so at start. What this cannot stop: an agent allowed the command line runs as the same user and can rewrite all of it, which is why that switch is red.
- **Routing/display state is tracked per target, not globally** (`activeRequestByTarget`, `busyTargets`, `displayQueue` in `agent-bridge-server.js`). A new request to one agent must never invalidate another agent's independent, still-running work — that was a real, previously-shipped bug.

## Verifying a change

There's no test suite — verification in this project means real, live behavior:
- `node --check <file>` after every edit, on every machine the file gets deployed to.
- For anything touching the marker regexes or routing logic, a throwaway Node script that connects fake nodes via `agent-net.js`'s `connectToHub()` and hand-crafts protocol messages is the fastest way to test hub logic with zero real API cost. Delete it when you're done.
- For anything touching what an agent actually says or decides, a short real `claude -p` call is worth the tokens — simulating both sides has hidden real bugs in this project before.
